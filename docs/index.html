04Het verhaal

Van "kan dit?" naar een duidelijke KV-les en een harde sweep-uitslag.

1️⃣De opdracht: Opus-klasse op een 2017-machine

De machine was al verkocht en stond op afhaling, maar de vraag was te mooi om te laten liggen: kan deze 4× V100-opstelling (128GB VRAM, sm_70) een Opus-klasse LLM serveren met 64k–200k context? Het eerder gebouwde gx10-project had de kwaliteits-methodologie al; dit project voegt de context-sweep toe die nog niemand had gedaan voor tweedehands Volta-hardware.

2️⃣De architectuur-drempel: Volta limiteert alles

Vóór de eerste benchmark bleek dat bijna de hele moderne inference-stack afvalt op sm_70: geen BF16/FP8-hardware, geen FlashAttention-2, geen Marlin 4-bit kernels. llama.cpp is de enige runtime — en dan alleen correct als je specifiek voor sm_70 compileert (CMAKE_CUDA_ARCHITECTURES=70), anders valt FlashAttention stilletjes weg. De bouw zelf kostte drie valkuilen: een glibc↔CUDA math-clash, de eis dat K en V dezelfde quant hebben voor FlashAttention, en het vermijden van BF16-KV op Volta.

3️⃣De KV-les: waarom alleen hybride modellen 200k halen

De doorslaggevende ontdekking. Dense 70B/72B-modellen zijn per token even duur in KV-cache als in gewichten (~320 KiB/token), waardoor 128k context al ~43GB aan KV vergt. De hybride Nemotron-familie draait het om: maar 6–8 van hun ~52–88 lagen zijn attention (de rest is Mamba, met een context-onafhankelijke toestand), dus een token kost er 6–8 KiB. Het gevolg is binair: Nemotron-3-Super serveerde 243k tokens (5/5 retrieval) in 87GB VRAM; een dense 70B zou bij 200k ~68GB aan KV alleen al nodig hebben.

4️⃣De sweep: hoe elk model faalt op 200k

Elk model werd doorgemeten op 8k/32k/64k/128k en daarna opzettelijk op 200k gezet om de faalmodus te vangen. Nemotron-3-Super en -3.5-Lightning haalden 5/5 tot en met 243k tokens — de enige twee die 200k echt halen. GPT-OSS-120B stopte op 117k (128k hard cap), Llama-3.3-70B op 79k, Qwen3.8-27B op 76k (open bug: stille EOS boven ~130k), en Qwen2.5-72B clamt al bij 32k native.

5️⃣De kwaliteits-batterij: waar de modellen zich onderscheiden

Op de 43/43-batterij staan GPT-OSS-120B en Nemotron-3-Super bovenaan (42/43); GPT-OSS is 2.3× sneller (110 vs 48 t/s) maar capped op 128k. Nemotron-3.5-Lightning is de snelste van allemaal (142 t/s) op 25.5GB, maar loopt op één kansreken-vraag leeg (thinking-runaway). Llama-3.3-70B faalt op tool-calling (2/4) door een llama.cpp parser-limiet, en Qwen2.5-72B zakt op rekenen (7/10) én context (32k).

05Belangrijkste lessen

📐

KV-geometrie bepaalt je context

Dense 70B/72B = ~320 KiB/token KV (128k ≈ 43GB). Hybride Mamba = 6–8 KiB/token. Wil je 200k? Kies op het aantal attention-lagen, niet op de gewichten.

🧱

Bouw voor sm_70, of verlies FlashAttention

Alleen CMAKE_CUDA_ARCHITECTURES=70 activeert de Volta-FA-pad; een multi-arch build valt stilletjes terug. En: geen BF16/FP8/Marlin op V100.

🌀

MoE/hybride > dense

Dense Llama-3.3-70B (16 t/s) vs hybride Nemotron-3.5 (142 t/s) ≈ 9× sneller. Op bandbreedte-gelimiteerde hardware wint de architectuur, niet de grootte.

🧭

Sweep tot de faalmodus

Test niet alleen de max, zet het model er opzettelijk overheen. Elk gecapped model faalde op zijn eigen manier: hard cap, stille EOS of native 32k.

🧠

Reasoning eet zijn eigen budget

Zonder ruim max_tokens (2000+) en enable_thinking:false voor formaat-taken lijkt een goed model plots "leeg" te antwoorden.

🔍

Verifieer zelf — tot de bestandsgrootte

De HF-API is de enige betrouwbare bron. Let op de content-vs-name-trap: unsloth's "UD-Q4_K_M" voor Nemotron-3-Super is écht ~5.5 bpw — vandaar 82.5GB, niet 68.

06Zelf reproduceren

Alle scripts zijn pure Python (stdlib) en praten met een lokale llama-server. Volledige uitleg: scripts/README.md.

git clone https://github.com/sayfjawad/c4130-llm-benchmarks.git
cd c4130-llm-benchmarks

# 1. Bouw llama.cpp alléén voor sm_70 (anders valt FlashAttention stilletjes weg)
cmake -B build -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=70 && cmake --build build -j

# 2. Download één model (GPT-OSS-120B, 63GB, native MXFP4)
pip install -U "huggingface_hub[cli]"
hf download ggml-org/gpt-oss-120b-GGUF --include "*MXFP4*.gguf" --local-dir ~/models/gpt-oss-120b

# 3. Start de server: 4 GPUs laag-gewijs, expliciete context + 1 slot
./build/bin/llama-server --model ~/models/gpt-oss-120b/gpt-oss-120b-MXFP4.gguf \
  --alias gpt-oss-120b --host 127.0.0.1 --port 8081 \
  --n-gpu-layers 999 --split-mode layer --tensor-split 8,8,8,8 \
  -c 131072 -np 1 -fa on --kv-unified -ctk q8_0 -ctv q8_0

python3 scripts/bench_hard.py 8081 gpt-oss-120b

💾 Schijfruimte: reken ~50GB voor kleine kandidaten (30-40GB klasse), ~130GB voor grote (~100GB klasse). Sequentieel testen (download → test → opruimen → volgende) houdt 150GB vrije ruimte ruim voldoende, ongeacht hoeveel modellen je wilt vergelijken.

📚 Bronnen: Hugging Face (modelgewichten, met name unsloth-GGUF-conversies) · llama.cpp (inference) · officiële Hugging Face API voor modelverificatie.
